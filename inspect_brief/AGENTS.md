# Repository Guidelines

## Project Structure & Module Organization
Core package code lives in `hirundo_evals/`. The CLI entry point is `hirundo_evals/run.py`, framework adapters live under `hirundo_evals/frameworks/`, and local vLLM lifecycle helpers live in `hirundo_evals/utils/vllm.py`. Tests should reside in `tests/` and mirror module names when added. Documentation sources are in `docs/`. Generated evaluation logs and summary CSVs should stay under ignored output directories such as `logs/`; distribution artifacts generated by releases land in `dist/` and should not be edited manually.

## Build, Test, and Development Commands
- `uv venv && source .venv/bin/activate`: create and activate the dedicated virtual environment before running tooling. Install dependencies into `.venv` rather than the system interpreter.
- `uv sync`: install the project locally; add `--extra mlflow`, `--extra vllm`, or both flags when you need those integrations.
- Dev containers run `.devcontainer/setup.sh`, which installs the base project by default; export `HIRUNDO_EVALS_INSTALL_EXTRAS="mlflow"` (or `mlflow,vllm`) before invoking the script if you require extras and have sufficient disk space.
- Prefer `uv` for dependency management in automation scripts and local workflows; avoid invoking `pip` directly unless you are installing `uv` itself or a tool explicitly requires `pip`.
- Run the CLI through the package entry point (`hirundo-evals ...`) or module form (`python -m hirundo_evals ...`) rather than executing files by path. The task argument is a comma-separated string, e.g. `hirundo-evals MODEL inspect-ai aime25,gpqa --limit 1`.
- this project uses `pytest`
- Run `ruff format .` (or `ruff format --check --diff` to verify) before committing to ensure consistent styling, followed by `ruff check .` for linting.
- `pyrefly check`: run static type checks (CI uses the same configuration).

## Coding Style & Naming Conventions
Follow PEP 8 defaults with 4-space indentation. Prefer `snake_case` for modules, functions, and variables; reserve `PascalCase` for classes and `UPPER_SNAKE_CASE` for constants. Keep public CLI options descriptive and aligned with existing Typer command names. Let `ruff` fix spacing and import order; avoid disabling rules unless there is a clear justification. Type hints are expected on new public functions. Framework-specific behavior should stay inside the relevant adapter in `hirundo_evals/frameworks/`; keep shared command execution, result schemas, and CSV export behavior in the base wrapper.

## Testing Guidelines
Add or update `tests/test_*.py` files alongside any new feature. Use `pytest` assertions, fixtures, and `monkeypatch` for mocking subprocesses, filesystem output, and framework calls (avoid `unittest.mock`). Cover CLI parsing in `hirundo_evals/run.py`, module execution via `hirundo_evals/__main__.py`, framework command construction, task alias mapping, log parsing, and CSV export behavior when those areas change. Keep simulated framework logs deterministic so runs remain reproducible.

## Commit & Pull Request Guidelines
Write imperative, concise commit titles (e.g., `Add hallu evaluator smoke tests`). Squash trivial fixups locally before raising a PR. Each PR should explain behavior changes, note impacts on benchmark outputs, and link to any tracking issue. Attach screenshots or sample CLI output when the change affects user-visible results. Mark configuration-sensitive updates (MLflow, datasets, prompt presets) so reviewers can double-check downstream pipelines.

## Security & Configuration Tips
No secrets should live in the repo. Use environment variables for provider tokens such as `HF_TOKEN`. We recommend using [`python-dotenv`](https://pypi.org/project/python-dotenv/) to load local secrets from an untracked `.env` file into environment variables, and never commit `.env` files or their contents. Local vLLM runs may set temporary environment values such as `CUDA_VISIBLE_DEVICES` and a dummy `OPENAI_API_KEY`; restore caller state after managed subprocesses exit. Verify that large artifacts stay out of version control and keep experimental outputs in ignored directories such as `logs/`.
